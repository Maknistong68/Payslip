# Offline Payslip Delivery Runs on Assisted Clicks

A browser-only page cannot send anything; it can only package payslips and hand each one to a program the employer already has, so the app should be built as a packager plus a "send list", not as a sender. The technical ceiling is firm: every browser action that reaches outside the page (a `mailto:`/`wa.me` link, the OS share sheet, a file download) consumes one user gesture and performs one action, so 1,000 payslips mean 1,000 operator clicks on any push channel; the only place one gesture unlocks a thousand writes is the Chromium File System Access API, which turns the page into a folder-of-named-PDFs generator. The only genuinely zero-click-per-employee free route is Thunderbird's Mail Merge add-on reading a CSV the app writes, and even that runs through the employer's own mailbox at provider limits (Exchange Online 30 messages/minute, free Gmail 500/day). WhatsApp is where the workers are (92.7% of Saudi internet users), but it is the costliest channel to operate (an estimated 6–11 operator-hours per pay cycle, by hand, from WhatsApp Desktop) and the riskiest legally, because every message to a worker is a PDPL cross-border disclosure and bulk new chats trip WhatsApp's own restriction machinery. Saudi law, meanwhile, does not require a payslip document, a worker signature or any delivery medium: the Labour Law obliges a wage register "paper or electronic", bank payment through the Wage Protection System, and the ability to show each deduction and its reason; the real constraints are evidentiary (keep a hashed, timestamped log per worker per month) and PDPL (security, 72-hour breach notice, and a draft data-localisation rule). The recommended build order is therefore: (1) a folder/ZIP export with stable file names and a delivery manifest, (2) a per-employee send list with one-click WhatsApp, share-sheet, mailto and `.eml` hand-offs plus a hashed delivery log, (3) password-protected PDFs with an honest "need-to-know, not secrecy" framing, (4) a combined print pack with an acknowledgement register and a camp-office kiosk mode, and (5) export packs for Thunderbird Mail Merge and classic-Outlook VBA for the minority of employers who can run them.

## One gesture buys one action, except when writing a folder

Everything the app wants to do with a finished PDF runs into the browser's user-activation model. Chrome allows "only one popup per user activation because `window.open()` consumes user activation", and a transient activation expires after a short interval ([Chrome Developers](https://developer.chrome.com/blog/user-activation)). Chromium's share service likewise rejects a call without transient activation and consumes it, so one click can never fan out into repeated share sheets ([Chromium source](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/webshare/share_service_impl.cc)). Downloads are rate-limited the same way: Chromium's `DownloadRequestLimiter` lets a page start one download, then moves it to "prompt before download", and a developer test of a loop of `<a download>.click()` calls left "only the last file downloaded" ([Chromium source](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/download/download_request_limiter.h); [zenn.dev](https://zenn.dev/foxtail88/articles/multiple-download)). The practical meaning is that a loop over 1,000 employees that opens links, shares files or triggers downloads is dead after the first iteration. The UI pattern that survives is a table of employees where each row's button performs exactly one action, preferably as a real `<a target="_blank">` rather than `window.open`, so every click is its own activation and no popup blocker fires.

The one exception is the File System Access API. `showDirectoryPicker({mode:'readwrite'})` needs a gesture once, then "access lasts until all tabs for the origin are closed", so 1,000 `getFileHandle(name,{create:true}) → createWritable() → close()` calls proceed without further prompts; Google's own guidance is to obtain the handle before slow work, because a picker called after a long async job fails when the gesture has expired ([Chrome Developers](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access)). Support is Chromium-only: **Chrome/Edge 86+ on desktop, Chrome 132+ on Android, never Firefox or Safari** ([MDN browser-compat-data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Window.json)). The Android implementation is intent-based, files are content URIs, atomic writes and renames are unsupported, and early testing found folder saves throwing `InvalidStateError` ([blink-dev](https://groups.google.com/a/chromium.org/g/blink-dev/c/x3IcFv2jY6c/m/HxuEfzBHAAAJ)), so phones should get the ZIP, not the folder writer. For Firefox and Safari the fallback is the ZIP the app already builds. JSZip keeps the whole archive in memory, roughly three times the archive size by a maintainer's estimate ([JSZip issue #343](https://github.com/Stuk/jszip/issues/343)); at 30–60 KB per Arabic payslip that is a 30–60 MB ZIP and ~100–200 MB of transient RAM, fine on a desktop. The app currently zips with DEFLATE level 6, which is wasted work: PDF streams are already Flate-compressed, and fflate's authors recommend level 0 for PDF ([fflate](https://github.com/101arrowz/fflate)); JSZip's own documentation says STORE-to-STORE avoids recompression ([JSZip limitations](https://stuk.github.io/jszip/documentation/limitations.html)). If zipping ever becomes the bottleneck, client-zip (6.4 kB, store-only, streams from an async generator) and fflate (~30 kB, streaming, Web Worker option) both benchmark faster than JSZip on thousands of small files ([client-zip](https://github.com/Touffy/client-zip)).

The Web Share API is the mobile and Windows 11 hand-off. `navigator.share({files})` is supported in Chrome desktop 89+ (full from 128), Chrome Android 76+, Edge 81+, Safari/iOS 14+, and **not at all in Firefox, desktop or Android** ([MDN browser-compat-data](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/Navigator.json); [caniuse](https://caniuse.com/web-share)). Chromium caps a share at **10 files and 50 MiB**, allowlists `.pdf`, and offers no way to choose the target app or recipient; the OS sheet does that ([Chromium source](https://chromium.googlesource.com/chromium/src/+/main/chrome/browser/webshare/share_service_impl.h)). Windows 11 lists WhatsApp in its share window from build 22631.3374, with an install prompt if absent ([Windows Developer Blog](https://blogs.windows.com/windowsdeveloper/?p=56290)). Two quirks matter for payslips: on iOS, passing both `text` and `files` makes Safari drop the files ([WebKit bug 251500](https://onbugs.webkit.org/show_bug.cgi?id=251500)), so the share call must pass files only; and Android WhatsApp rejects a PDF whose MIME type is wrong ([B4X forum](https://b4x.com/android/forum/threads/share-pdf-file-to-whatsapp.80770/?amp=1)), so construct the `File` with `application/pdf`.

Whether any of this works when `index.html` is double-clicked from a USB stick is the single most important thing to test before building. The research notes disagree: one infers that `file://` is not a secure context and that share-from-a-local-file is therefore blocked, while the primary sources say the opposite. MDN's secure-context page lists `file:///path/to/resource.html` as secure, and Chromium's own secure-origin definition includes `(file, *, —)` alongside `https` ([MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts); [Chromium security](https://www.chromium.org/Home/chromium-security/prefer-secure-origins-for-powerful-new-features/)). The spec marks `share()` and `showDirectoryPicker()` as `[SecureContext]`, so both APIs should be *defined* on a local page in Chrome and Edge; what no source confirms is that the Windows share sheet or the directory picker actually appears from a `file://` origin. Treat it as a one-hour empirical test (`window.isSecureContext`, `typeof navigator.share`, then a real call) on Windows, macOS and Android. If it fails, hosting the same static files on an HTTPS host such as Vercel preserves the "no backend" constraint while guaranteeing a secure context; the app can detect `location.protocol` and show the right buttons either way.

## Email without a server works only in classic Outlook or through Thunderbird

A `mailto:` link is the weakest email option. RFC 6068 forbids MIME structure, says the `body` is "primarily intended for the generation of short text messages", and tells clients to ignore any Content-* header, so there is no standards-based way to attach a PDF ([RFC 6068](https://datatracker.ietf.org/doc/html/rfc6068)). Practical length is about 2,000 characters: Chrome on Windows misbehaves at 2,048 ([personaldata.io](https://wiki.personaldata.io/wiki/Special:MobileDiff/2578)), and Gmail's web handler accepts roughly 4,096 after encoding ([codeforboston/maple](https://github.com/codeforboston/maple/issues/1964)). Arabic text triples in size after UTF-8 percent-encoding, so an Arabic body of ~300 characters already approaches the limit. A `mailto:` row in the send list is still worth having as a pre-addressed, pre-subjected message into which the operator drags the matching PDF, but it is a three-action-per-employee path.

A generated `.eml` file carries the PDF inside the message and is trivial to build: CRLF lines, `multipart/mixed`, a `text/plain; charset=utf-8` part, and an `application/pdf` part base64-wrapped at 76 characters per RFC 2045 ([RFC 2045](https://www.rfc-editor.org/rfc/rfc2045)); Arabic subjects go in RFC 2047 encoded-words ([RFC 2047](https://datatracker.ietf.org/doc/html/rfc2047)). Whether double-clicking it yields a sendable draft depends entirely on the client. **Classic Outlook for Windows opens an `.eml` as an editable draft only when the header `X-Unsent: 1` is present**, a behaviour change since build 16.0.14430.20256 (Version 2109) ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4562029/eml-files-no-longer-opening-as-a-draft-e-mail-to-s)). New Outlook has been erratic: in May 2024 a Microsoft moderator said draft editing "isn't currently feasible in New Outlook for Windows" ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/4635248/header-x-unsent-for-eml-files-is-not-recognized-in)); by September 2025 drafts opened but could be sent only once unless the `Message-ID` line was removed ([Microsoft Q&A](https://learn.microsoft.com/en-au/answers/questions/5562698/new-outlook-eml-x-unsent-1-sending-not-working-mul)); and from September 2025 to January 2026 new `.eml` files failed to save to Drafts until Outlook began requiring a valid `Message-ID` next to `X-Unsent`, reportedly fixed in Version 1.2026.105.100 ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/5594291/new-eml-files-will-not-save-to-draft-folder-(fixed)). Outlook for Mac does not honour the header, Apple Mail ignores it and uses its own draft marker, and Thunderbird opens the file read-only, requiring "Edit As New Message" (Ctrl-E) ([Aspose forum](https://forum.aspose.com/t/saving-eml-as-unsent-not-working-on-mac/17643); [Rebex forum](https://forum.rebex.net/9290/save-email-as-unsent-using-eml-in-apple-mail); [Mozilla Support](https://support.mozilla.org/de/questions/1022415)). Generating `.msg` instead is not realistic in a vendored offline bundle: the only open-source writer, tutao/oxmsg, is GPL-3.0, Node-only and unfinished ([GitHub](https://github.com/tutao/oxmsg)). So the `.eml` export is a two-clicks-per-employee path for Windows offices on Outlook, and should be written with `X-Unsent: 1`, a unique `Message-ID`, `MIME-Version`, an RFC 2047 subject and an ASCII-safe attachment filename, then tested on the exact Outlook build the morning of the payroll run.

True bulk sending means a mail-merge tool, and Microsoft's own has a hole in it: Word's merge-to-email "does not support merging attachments with the message", leaving an add-in or VBA as the only fixes ([Slipstick](https://www.slipstick.com/outlook/mail-merge-using-outlook)). Doug Robbins' free Merge Tools Add-in adds "Mail Merge with Attachments" from a data-source column but is Windows plus classic Outlook only and distributed as a zip by an individual MVP ([mergetoolsaddin.com](https://www.mergetoolsaddin.com/)); MAPILab's Mail Merge Toolkit does the same for about US$24 per user ([Software Advice](https://www.softwareadvice.co.uk/software/319051/mail-merge-toolkit)). A twenty-line VBA loop using `Application.CreateItem(olMailItem)` and `.Attachments.Add` works in classic Outlook, and because in-process code uses the trusted `Application` object it avoids the Object Model Guard; run the same loop from PowerShell or Excel and, unless Windows Security Center reports antivirus "Good", every `.Send` raises a warning whose Allow button is disabled for five seconds and covers only that one call ([Microsoft Learn](https://learn.microsoft.com/en-us/office/vba/outlook/how-to/security/outlook-object-model-security-warnings); [Microsoft Learn](https://learn.microsoft.com/en-us/office/vba/outlook/how-to/security/security-behavior-of-the-outlook-object-model)). The remaining hurdle is the default macro setting, which disables unsigned macros. All of this dies with new Outlook, which "doesn't support VBA and Macros", COM add-ins or MAPI automation ([Microsoft Learn](https://learn.microsoft.com/en-us/microsoft-365-apps/outlook/get-started/vba-alternatives); [Microsoft Q&A](https://learn.microsoft.com/en-in/answers/questions/5951650/need-a-support-in-new-outlook-automation)).

That leaves Thunderbird. Alexander Bergmann's Mail Merge add-on is free, actively maintained (v11.5.0 on 31 March 2026 added Thunderbird 150 support, compatible with 128 ESR and 140 ESR), and takes a per-row `{{Attachment}}` column ([addons.thunderbird.net](https://addons.thunderbird.net/hu/thunderbird/addon/mail-merge/versions)). Its workflow is a CSV with an attachment column, a configurable pause between messages, and a "Save as Draft" or "Send Later" mode for review ([FSFE wiki](https://wiki.fsfe.org/TechDocs/MailMerge)). The catch since Thunderbird 102 is that the attachment field only accepts filenames and the files must first be multi-selected with the Browse button because of MailExtension API limits ([Mozilla Support](https://support.mozilla.org/ro/questions/1325172)), which is exactly why the app's export should put all 1,000 PDFs in one flat folder with names that match the CSV. The add-in's author also warns that legacy Experiment add-ons stop running on the Thunderbird release channel from version 153, so the recommendation is ESR.

Whatever client sends, the mailbox's provider meters the run. Exchange Online allows **10,000 recipients per day but only 30 messages per minute**, with excess "throttled and successively carried over", so 1,000 individual messages take at least 34 minutes, and mail from the default `*.onmicrosoft.com` domain is capped at 100 external recipients per organisation per day ([Microsoft Learn](https://learn.microsoft.com/en-us/office365/servicedescriptions/exchange-online-service-description/exchange-online-limits)). Google Workspace allows 2,000 messages per user per day (1,500 via its native mail merge, which cannot vary the attachment per recipient), and blocks sending for up to 24 hours when exceeded ([Google Workspace Admin Help](https://knowledge.workspace.google.com/admin/gmail/gmail-sending-limits-in-google-workspace)); free Gmail stops at 500 per day ([Mailmeteor](https://mailmeteor.com/blog/email-sending-limits)); Outlook.com with a Microsoft 365 subscription allows 5,000 recipients but only 1,000 "non-relationship" recipients per day ([Microsoft Support](https://support.microsoft.com/en-us/office/sending-limits-in-outlook-com-279ee200-594c-40f0-9ec8-bb6af7735c2e)). A small employer on free Gmail must split the run over two or three days, and one on a trial Workspace tenant (500/day) likewise. The deeper problem is upstream of all of these: a blue-collar workforce largely has no corporate mailbox, and sending to personal Gmail or Hotmail addresses counts as external recipients for the Microsoft caps. Email is the right channel for office staff and the wrong primary channel for NEOM site labour.

## WhatsApp reaches almost everyone and costs the most to operate

Reach is not in question. The CST's Saudi Internet Report 2025 puts WhatsApp first among platforms at **92.7% usage** with internet penetration at 99.6% ([CST via Minute Mirror](https://minutemirror.com.pk/whatsapp-is-most-used-app-in-saudi-arabia-report-finds-620330/)), and low-income migrants in the Gulf "typically have smartphones" even when they fall below the salary floor for a bank account ([CFI.co](https://cfi.co/awards/wp-json/wp/v2/posts/9570)). No survey broken down by migrant or construction status was found, so smartphone ownership in a NEOM camp is an inference from general figures and from migrants' heavy mobile-money use ([GSMA](https://www.gsma.com/solutions-and-impact/connectivity-for-good/mobile-for-development/mobile-for-development-2/how-mobile-money-empowers-social-security-payments-via-migrants-remittances/)); data allowances are metered, which argues for small files and against cloud links.

What WhatsApp will not do is accept a file from a link. The official click-to-chat form is `https://wa.me/<number>?text=<urlencoded>` with the number "in international format" and without zeros, brackets or dashes; the only parameters are the phone and the text ([WhatsApp Help Center](https://faq.whatsapp.com/5913398998672934/)). For a Saudi mobile that is `966` plus nine digits with the leading zero dropped, a consistent 12-digit E.164 number ([sent.dm](https://sent.dm/en/resources/phone-number-standards/sa)); many migrants keep home-country SIMs, so the generator must accept any E.164 number rather than assuming +966. The PDF then has to be attached by hand: WhatsApp Web and Desktop take documents up to 2 GB via "+" then Document, or by dragging the file into the text field ([WhatsApp Help Center](https://faq.whatsapp.com/453914586839706/)). There is one trap on macOS: Macwelt reported on 30 April 2026 that in WhatsApp for Mac 26.14.xy and later, dragging a document into a chat and sending it **irreversibly deletes the original from its Finder folder**, with the "+" button as the safe workaround ([Macwelt](https://www.macwelt.de/article/3128392/whatsapp-bug-mac-dokumente.html)); the app's instructions for Mac users must say "use +, never drag". The Web Share path is the alternative hand-off: on Android the operator taps Share, picks WhatsApp, then picks the contact; on Windows 11 the share window hands the PDF to the WhatsApp app, which then asks for a recipient. Share and click-to-chat cannot be combined into one action, so each saves a different set of steps and the send list should offer both.

Broadcast lists do not help. A list holds at most 256 contacts, delivers only to people who have saved the sender's number, cannot be used from Windows, Mac or Web, and sends the same payload to everyone ([WhatsApp Help Center](https://faq.whatsapp.com/861663048350950/)), so at best it carries a "your payslip is ready" notice. Quick replies cannot include media on Web or Desktop either ([WhatsApp Help Center](https://faq.whatsapp.com/1791149784551042/)). The realistic workflow is therefore: click the row's `wa.me` link, WhatsApp Desktop opens the chat with a pre-filled greeting that names the employee and the month, press Enter, drag or attach the matching PDF from an adjacent Explorer window, confirm, tick the row. With files and rows sorted identically that is roughly 5–7 interactions and 20–40 seconds per employee, or **about 6–11 operator-hours for 1,000 workers per pay cycle**; this is an estimate from the research, as no published measurement exists. For contrast, the paid WhatsApp Business Platform charges Saudi utility messages at roughly US$0.012 each ([SleekFlow](https://help.sleekflow.io/en_US/whatsapp/pricing)), about US$12–15 a month for 1,000 payslips before BSP fees, which is the number to hold up when an employer weighs a day of clerical time against the "no API" constraint.

The account-level risk is real and asymmetric. WhatsApp states that "any user engaging in spam, automated, or bulk messaging could have their account banned", and that a restricted account "can't start chats or calls with new contacts" or use linked devices while the restriction lasts ([WhatsApp Help Center](https://faq.whatsapp.com/717472490411581/)); temporary bans escalate to permanent ones for unofficial clients ([WhatsApp Help Center](https://faq.whatsapp.com/1848531392146538)), and a WhatsApp Business ban with no "Request review" option is final ([WhatsApp Help Center](https://faq.whatsapp.com/723378546580115)). The Business Policy requires opt-in and prohibits "messaging people at scale in an unauthorized manner" ([WhatsApp Business Policy](https://whatsappbusiness.com/policy/)). Opening a thousand chats with numbers that have never messaged HR is precisely the "many new chats to strangers" pattern vendors describe as the restriction trigger, and the restriction disables linked devices, which would cut off WhatsApp Desktop mid-run. Chrome-extension "bulk senders" attach one file per campaign, not one per contact, and sit squarely in the unauthorised-tool category ([Privyr](https://www.privyr.com/blog/whatsapp-bans-automated-bulk-send/)). The mitigations that follow from WhatsApp's own wording are: import all workers as saved contacts on the HR phone, have every worker message HR once first (a printed QR poster with `wa.me/<HR number>?text=<employee ID>` does this and creates the opt-in record), send from the official Business app on a dedicated number, pace the run at a couple of hundred per hour, and stop the moment a restriction banner appears. Confidentiality is weaker than the end-to-end-encryption label suggests: WhatsApp's own E2EE backups are optional, and by default Google Drive and iCloud backups are not end-to-end encrypted ([WhatsApp blog](https://blog.whatsapp.com/end-to-end-encrypted-backups-on-whatsapp); [ExpressVPN guide](https://expressvpn.com/blog/enable-end-to-end-encryption-in-whatsapp)), so the PDF should be password-protected and free of full bank account numbers, and the pre-filled greeting should carry the worker's name so a wrong digit is caught before the attachment goes.

## Kiosks, paper, QR stubs and passwords serve workers without mailboxes

For a camp workforce the pull channels beat the push channels on every axis except HR effort, and the app can make them cheap. The strongest fit is a kiosk mode at the camp office: HR self-service kiosks that authenticate a worker by RFID, fingerprint or national ID plus SMS OTP and print payslips on the spot are an established product category ([Creasoft](https://creasoft.ro/en/employees-info-kiosk)), and Workday exposes the same "let workers print their own payslips" control in its admin guide ([Workday](https://doc.workday.com/admin-guide/en-us/payroll/payslips/aop1491007974493.html)). The static page can do this with no network: a locked-down tab on the office PC where the worker types an Iqama number and a second factor (date of birth or a supervisor-issued PIN, because an Iqama alone is guessable and printed on badges), the page renders that one slip, prints it, and appends a timestamped line to a local print log. The worker needs no phone, no data and no literacy beyond ten digits; HR needs a staffed PC, a printer and a queue plan for a few hundred prints a day over the pay week.

Printed hand-out with a signed acknowledgement register is the zero-technology fallback and the artefact a labour inspector most readily understands, even though nothing in Saudi law mandates it. The app already builds one combined PDF; the print pack should add an A4 register per department (employee ID, name, net, signature, date) and a slip layout that folds to hide the figures, since paper is the one channel with no confidentiality at all. Bulk printing should go through one merged PDF opened in a tab and printed from the browser's viewer: printing a PDF from an iframe via `contentWindow.print()` has failed in Firefox since a 2013 bug ([Bugzilla 856116](https://bugzilla.mozilla.org/show_bug.cgi?id=856116)), and iOS Safari renders an embedded PDF as a single first page ([WebKit bug 253671](https://onbugs.webkit.org/show_bug.cgi?id=253671)).

QR codes earn a place on the slip but cannot carry it. Capacity tops out at **2,953 bytes** at version 40, error-correction level L ([Keyence](https://www.keyence.com/ss/products/auto_id/codereader/basic_2d/qr.jsp)), so a payslip PDF of tens of kilobytes never fits; a short text summary (ID, month, basic, allowances, deductions, net, in Arabic and English labels) does, and any phone camera decodes it offline, which makes a printed QR stub the one zero-data, any-phone, no-app option. A `wa.me` link QR needs connectivity and WhatsApp when scanned, which is fine for a "contact HR" or opt-in code and wrong for the whole payslip. Generation is fully offline with `qrcode-generator` (MIT, single script, `createDataURL()`) or `node-qrcode` (MIT, `toDataURL()`), both dropping straight into `doc.addImage()` as PNG data URLs ([qrcode-generator](https://github.com/kazuhikoarase/qrcode-generator); [node-qrcode](https://github.com/soldair/node-qrcode); [jsPDF addImage](https://artskydj.github.io/jsPDF/docs/module-addImage.html)); Arabic payloads need the library's byte mode fed from `TextEncoder`.

Password protection is where honesty matters most. jsPDF has encrypted since v2.2.0 (PR #2959) and the project's vendored 2.5.x builds carry it, but the implementation is the Standard handler at `V=1`, `R=2`, a 5-byte key, that is **40-bit RC4 derived with MD5** ([jsPDF release](https://github.com/parallax/jsPDF/releases/tag/v2.2.0); [jsPDF pdfsecurity.js](https://raw.githubusercontent.com/parallax/jsPDF/master/src/libs/pdfsecurity.js)). Chrome and Edge's PDFium and Firefox's pdf.js both still open R2 files and default a missing `/Length` to 40 bits ([PDFium](https://pdfium.googlesource.com/pdfium/+/main/core/fpdfapi/parser/cpdf_security_handler.cpp); [pdf.js](https://raw.githubusercontent.com/mozilla/pdf.js/master/src/core/crypto.js)), but nothing confirms Adobe Reader, iOS Quick Look or WhatsApp's in-app viewer, and two jsPDF issues (no password prompt in Safari; garbled strings with a custom font plus `userPassword`) must be retested with the bundled Amiri font ([jsPDF issues](https://github.com/parallax/jsPDF/issues?q=encryption+password)). The cheapest AES-256 upgrade that stays offline and MIT-licensed is to post-process each `doc.output('arraybuffer')` with `@pdfsmaller/pdf-encrypt` (~17 KB gzipped, AES-256 R6 by default, needs pdf-lib and Web Crypto, use ≥1.1.0) or the `@cantoo/pdf-lib` fork's `encrypt()` ([pdf-encrypt README](https://cdn.jsdelivr.net/npm/@pdfsmaller/pdf-encrypt@1.0.2/README.md); [@cantoo/pdf-lib README](https://cdn.jsdelivr.net/npm/@cantoo/pdf-lib/README.md)); qpdf compiled to WASM (`pdfstudio`, Apache-2.0) is the most battle-tested engine but weighs about 2.1 MB ([pdfstudio README](https://cdn.jsdelivr.net/npm/pdfstudio@0.4.0/README.md)), and mupdf.js is AGPL ([mupdf package.json](https://cdn.jsdelivr.net/npm/mupdf/package.json)).

Stronger ciphers do not rescue weak passwords, and the passwords workers can remember are weak. Gulf payroll products default to the full employee ID plus day-and-month of birth (HRWorks), date of birth or ID number (BrioHR), or employee ID, passport or DOB (Sage) ([HRWorks](https://hinote.atlassian.net/wiki/spaces/HUG/pages/590058/Payslip+and+Tax+Sheet+Password); [BrioHR](https://support.briohr.com/knowledge/enhance-payslip-security-with-password-protected-payslips); [Sage](https://communityhub.sage.com/cfs-file/__key/communityserver-discussions-components-files/386/Adding-passwords-to-payslips.pdf)). A ten-digit Iqama is a keyspace of at most 10^10, and about 10^9 if the leading digit is assumed. Community hashcat figures put legacy PDF cracking (mode 10500) near 3 MH/s per mid-range GPU and AES-256 R6 (mode 10700) at ~14.5 kH/s on an old GTX 970 ([hashcat forum](https://hashcat.net/forum/printthread.php?tid=7021); [hashcat forum](https://hashcat.net/forum/printthread.php?tid=11838)); the arithmetic is roughly **5–55 minutes** to exhaust an Iqama against jsPDF's RC4-40 and **19 hours to 8 days** against AES-256 R6 on one old card, hours on a modern one. The right framing in the UI and the documentation is that the password stops a co-worker or clerk from casually opening someone else's slip and satisfies "need-to-know", not that it provides confidentiality; AES-256 is still worth shipping because it raises the cost by three orders of magnitude for a few dozen kilobytes of library. Per-employee cloud folders fail on every count for this population: OneDrive's "Request files" is upload-only and cannot distribute anything ([SharePoint Diary](https://www.sharepointdiary.com/?p=21714)), hand-creating and sharing 1,000 folders monthly is tens of HR hours, and each worker would need an account, data and the literacy to navigate a cloud UI. A shared drive or USB handed to a site supervisor, holding only password-protected PDFs, is the acceptable low-tech middle ground.

## Saudi law allows e-payslips but makes the channel a PDPL decision

The Labour Law contains no article that obliges an employer to hand each worker a payslip, prescribes its contents, requires a signature or sets a payslip-specific retention period. The anchor is Article 17, which requires the employer to keep at the workplace the records specified in the Regulations ([Labour Law, HRDF consolidation](https://hrdf.org.sa/media/eacale2o/labor-low-en.pdf)), implemented by Article 5 of the 2025 Implementing Regulations (Ministerial Decision 115921, in force 19 February 2025), which mandates a wage register containing wages, the dates workers received them, every deduction and its reason, and applies to records kept "سواء أكانت ورقية أم الكترونية", **whether paper or electronic** ([Implementing Regulations, MHRSD PDF](https://www.hrsd.gov.sa/sites/default/files/2025-04/%D8%A7%D9%84%D9%84%D8%A7%D8%A6%D8%AD%D8%A9%20%D8%A7%D9%84%D8%AA%D9%86%D9%81%D9%8A%D8%B0%D9%8A%D8%A9%20%D9%84%D9%86%D8%B8%D8%A7%D9%85%20%D8%A7%D9%84%D8%B9%D9%85%D9%84%20%D9%88%D9%85%D9%84%D8%AD%D9%82%D8%A7%D8%AA%D9%87%D8%A7.pdf)). Two claims circulating in vendor material do not survive contact with the text: Qoyod's assertion that "Article 70" ties worker rights to a salary receipt kept five years (Article 70 actually caps disciplinary fines) ([Qoyod](https://academy.qoyod.com/en/templates/salary-receipt/)), and a Mondaq piece claiming that 2025 amendments require monthly electronic payslips with five-year retention, which cites no article and matches nothing in the consolidated law or the 2025 Regulations ([Mondaq](https://www.mondaq.com/saudiarabia/employee-rights-labour-relations/1627664/saudi-labor-law-amendments-key-changes-in-2025)). The app should not tell employers that the law requires any particular format.

What the law does require shapes the slip's content and the proof HR must keep. Article 90(2) mandates deposit of wages into bank accounts through approved banks, Article 92 lists the only deductions permitted without written consent, Article 93 caps total deductions at half the wage, and Article 94 lets the labour court fine an employer up to twice any wrongly deducted or delayed amount ([Labour Law, HRDF consolidation](https://hrdf.org.sa/media/eacale2o/labor-low-en.pdf)). The Wage Protection Program's monthly Mudad file carries basic salary, housing allowance, other allowances, total deductions, net, ID/Iqama and bank details, is rejected when net does not equal basic plus housing plus other minus deductions, and MHRSD describes the program as letting employers "prove wage payment without receipt sheets" and as "the reference for resolving workers' complaints" ([MHRSD, Wage Protection Program](https://hrsd.gov.sa/ar/initiatives/%D8%A8%D8%B1%D9%86%D8%A7%D9%85%D8%AC-%D8%AD%D9%85%D8%A7%D9%8A%D8%A9-%D8%A7%D9%84%D8%A3%D8%AC%D9%88%D8%B1)). Since August 2025 Mudad also raises alerts for deductions above 50%, basic wages unrecorded for 90 days and workers with no payment record, with inspection after 20 days without a file ([Okaz](https://www.okaz.com.sa/economy/na/2208645); [DLA Piper](https://knowledge.dlapiper.com/dlapiperknowledge/globalemploymentlatestdevelopments/2025/new-wage-monitoring-system-to-crack-down-on-salary-violations)). The WPS record proves a net amount reached the bank; only the payslip shows the worker how it was computed, which is what Articles 92–94 turn on. The practical consequence is that the payslip's line items should mirror the Mudad fields exactly (basic, housing, other allowances, each deduction with its reason, net) so that the Qiwa contract, the Mudad file and the slip reconcile.

Proof of delivery is an evidence question, not a signature question. Under the Evidence Law, digital correspondence is digital evidence; unofficial digital evidence binds the parties where it comes from a digital means stipulated in the contract, and a party who refuses without excuse to produce what the court requests to verify digital evidence loses the right to rely on it ([Sahal Law Firm](https://www.sahalfirm.com/t-en/blog/%D9%88%D8%B3%D8%A7%D8%A6%D9%84-%D8%A7%D9%84%D8%A5%D8%AB%D8%A8%D8%A7%D8%AA-%D9%81%D9%8A-%D8%A7%D9%84%D9%82%D8%B6%D8%A7%D9%8A%D8%A7-%D8%A7%D9%84%D9%85%D8%AF%D9%86%D9%8A%D8%A9-%D9%88%D8%A7%D9%84%D8%AA%D8%AC%D8%A7%D8%B1%D9%8A%D8%A9)); electronic records are treated as originals where integrity is maintained ([Latham & Watkins](https://www.lw.com/people/admin/upload/SiteAttachments/Understanding-the-Enforceability-and-Admissibility-of-Electronic-Signatures-in-Saudi-Arabias-Evolving-Legal-System.pdf)). An employer therefore gains most by naming the channel in the contract or work regulation ("payslips are issued via the company's registered WhatsApp number / e-mail / collection at the camp office") and by keeping, per worker per month, a log of recipient, timestamp, channel and the PDF's hash. A worker-signed "I accept the amounts" line adds little, because Article 8 voids any waiver of statutory rights, and Article 51 lets the worker prove entitlements "by all methods of proof" ([Labour Law, HRDF consolidation](https://hrdf.org.sa/media/eacale2o/labor-low-en.pdf)). Retention has no payslip-specific statute; claims are barred twelve months after the relationship ends (Article 222), so employment plus at least a year is the floor, five years is common policy, and PDPL requires the chosen period to be written into the record of processing ([PDPL, SDAIA](https://sdaia.gov.sa/en/SDAIA/about/Documents/Personal%20Data%20English%20V2-23April2023-%20Reviewed-.pdf)).

PDPL is where channel choice bites. Salary data is personal data, and Article 1(4) lists "bank and credit card numbers" explicitly; the lawful basis for issuing payslips is Article 6(2) (performance of the employment agreement and compliance with law), so consent is neither needed nor advisable as the basis because it can be withdrawn; Article 19 obliges "all the necessary organizational, administrative and technical measures" including during transfer; and Article 20 requires breach notification to SDAIA, which guidance sets at **72 hours with no de minimis threshold**, plus notice to the worker where prejudice is possible ([PDPL, SDAIA](https://sdaia.gov.sa/en/SDAIA/about/Documents/Personal%20Data%20English%20V2-23April2023-%20Reviewed-.pdf); [Baker McKenzie](https://connectontech.bakermckenzie.com/saudi-arabia-publishes-guidance-on-data-breach-notification/)). A payslip sent to the wrong WhatsApp number is a reportable breach. Sending through WhatsApp or a personal Gmail is also a transfer outside the Kingdom under Article 29: it must fit a permitted purpose, the natural one being "performance of an obligation to which the Data Subject is a party", and must rest on an adequacy finding (none published as of September 2026), an appropriate safeguard (SCCs or BCRs, which cannot be signed with a consumer app), or the contract-necessity derogation, whose strength falls whenever a domestic alternative such as a corporate mailbox or office collection exists ([Securiti](https://securiti.ai/regulation-on-personal-data-transfer-outside-the-kingdom); [Baker McKenzie via Global Compliance News](https://www.globalcompliancenews.com/2024/09/17/https-insightplus-bakermckenzie-com-bm-data-technology-saudi-arabia-updates-data-transfer-regulations-and-introduces-the-first-set-of-standard-contractual-clauses_09042024/)). SDAIA's draft Implementing Regulation amendments, under consultation from 6 October to 5 November 2026, would add a requirement to store personal data inside the Kingdom and require privacy notices in the language customarily used with data subjects ([Clyde & Co](https://www.clydeco.com/en/insights/2026/10/sdaia-publishes-draft-amendments-to-the-pdpl)). Enforcement is live: 48 SDAIA committee decisions by mid-January 2026, with violation categories including disclosure without legal basis and inadequate safeguards, five days to respond to a notice, and fines up to SAR 5 million ([Clyde & Co](https://www.clydeco.com/en/insights/2026/03/enforcement-of-the-saudi-pdp-law)). None is publicly an HR case, and no SDAIA guidance on messaging apps exists, so this is risk assessment, not settled law. The static app itself is the compliant part of the picture, since the workbook and PDFs never leave the employer's PC; the exposure is entirely in the hand-off, which is why the delivery features below default to the least-exporting option and record which channel each worker chose. NEOM adds no public rule: its Supplier Code of Conduct is not retrievable and it states only that contractors must follow a Code "based on the laws of Saudi Arabia and the policies of the International Labour Organization" with frequent inspections ([Business & Human Rights Resource Centre](https://www.business-humanrights.org/en/latest-news/saudi-arabia-itv-finds-migrants-constructing-the-line-at-megacity-project-neom-experience-egregious-labour-rights-abuse/)); an itemised slip in a language the worker reads is the practical way to evidence ILO-style wage transparency, and the binding clauses, if any, will be in the contract schedules.

## Build order: five delivery features, in priority

The comparison across channels is summarised below before the build plan; effort figures are estimates from the research, not measured.

| Channel | Operator effort per 1,000 | Reaches site labour | Proof of delivery | PDPL exposure | Verdict |
|---|---|---|---|---|---|
| Folder/ZIP export + shared drive or USB to supervisor | Minutes | Via supervisor | Weak unless paired with register | Low (stays in KSA) | Build first; foundation for everything else |
| WhatsApp Desktop via send list | ~6–11 h | Yes (92.7% usage) | Delivery ticks in app chat | High (foreign-hosted, mis-send = breach) | Build, with guard-rails |
| Share sheet (Android/Windows 11) | ~6–11 h | Yes | Same as above | High | Build as alternate button |
| `.eml` drafts (classic Outlook) | ~2,000 clicks | No (office staff only) | Sent Items | Medium (corporate mailbox) | Build, second tier |
| Thunderbird Mail Merge pack | Near zero after setup | No | Sent folder | Medium | Build export pack |
| Classic Outlook VBA pack | Near zero after macro trust | No | Sent Items | Medium | Ship script, low priority |
| Kiosk print at camp office | Staffed PC, multi-day | Yes, no phone needed | Print log | Lowest | Build, second tier |
| Printed pack + acknowledgement register | Printing + hand-out | Yes | Signed register | Lowest (paper privacy weak) | Build, cheap extension of existing PDF |
| QR text stub on slip | None | Yes, any phone, offline | None | Low | Build as option |
| Per-employee cloud folders, OneDrive Request files, broadcast lists, bulk-sender extensions, `.msg` generation | — | — | — | — | Do not build |

**Priority 1: folder export, stable names and a delivery manifest.** On Chromium desktop, add "Save all to a folder" that calls `showDirectoryPicker({mode:'readwrite', id:'payslips', startIn:'documents'})` on the button click before any PDF is generated, then writes `Payslips_2026-09/<Department>/<EmpID>_<YYYY-MM>_<Name>.pdf` one file at a time, yielding to the event loop every few dozen files so the progress bar stays truthful. Keep the ZIP for Firefox, Safari and phones, but switch it to `compression: 'STORE'`. Write a `manifest.csv` into the same folder with employee ID, name, phone in E.164, email, file name, SHA-256 of the PDF (via `crypto.subtle.digest`), net amount and a "preferred channel" column read from the workbook. File names must be ASCII-safe with the employee ID first, because every downstream hand-off (Explorer drag into WhatsApp, Thunderbird's Browse multi-select, the VBA loop) depends on matching a row to a file by name. Known limitations: Chromium-only folder writing, untested from `file://`, and Android's intent-based implementation is unreliable for a thousand files.

**Priority 2: the send list and the delivery log.** Generate an HTML page (also saved into the export folder so it works after the tab closes) with one row per employee and one-click actions: a `wa.me/<E.164>?text=<greeting with name and month>` anchor with `target="_blank"`; a Share button shown only when `navigator.canShare({files:[pdf]})` is true, passing files only; a `mailto:` anchor kept under 2,000 encoded characters; a Download `.eml` button; and a Download PDF button. Each click is its own activation, so no popup blocker fires. A "sent" checkbox persists to `localStorage` and the page exports the log as CSV with timestamp, channel, operator initials and the PDF hash, which is the artefact that answers a labour-court request under the Evidence Law. Build the guard-rails into this page rather than into instructions: normalise phones to E.164 and flag numbers that are not 12 digits for +966, flag duplicates, put the worker's name and month in the pre-filled WhatsApp text so the operator checks the chat header before attaching, and show a one-line macOS warning to attach with "+" rather than dragging. Sort rows in the same order as the files. Known limitations: no automatic sending, roughly 6–11 operator-hours per cycle for 1,000 workers on WhatsApp, no Web Share in Firefox, and the HR WhatsApp number remains exposed to restriction if the opt-in and pacing advice is ignored.

**Priority 3: password-protected PDFs, framed honestly.** Enable jsPDF's built-in `encryption: {userPassword, ownerPassword, userPermissions:['print']}` now, with the password derived from a configurable pattern (default employee ID plus date of birth as DDMM, matching Gulf vendor practice; Iqama alone as a weaker option) and communicated to workers out of band by the supervisor. Test the output in Acrobat Reader, iOS Files, Android WhatsApp's viewer and Safari, and with the Amiri font, before shipping. Plan the upgrade to AES-256 R6 by post-processing each PDF with `@pdfsmaller/pdf-encrypt` plus pdf-lib (both MIT), measuring the per-file cost across 1,000 slips. In the UI, label the feature "stops casual opening" rather than "secure", and strip full IBANs from the slip body (last four digits suffice) because the PDF will travel through consumer apps. Known limitations: 40-bit RC4 until the upgrade, a numeric keyspace that falls in minutes to days regardless of cipher, and viewer compatibility that must be empirically confirmed.

**Priority 4: print pack, acknowledgement register and kiosk mode.** Extend the existing combined PDF into a print pack per department: slips in a fold-to-conceal layout, followed by a register page (ID, name, net, signature, date) for the supervisor. Open it in a new tab for printing instead of relying on iframe `print()`. Then add a kiosk mode: a locked view of the same page on the camp-office PC where a worker enters an Iqama number plus date of birth or a PIN, sees nothing but a "Print my payslip" button, and the page appends ID, timestamp and PDF hash to a local print log the operator exports at the end of the pay week. Because the workbook would sit on a shared PC, kiosk mode should load an encrypted copy of the dataset (AES-GCM via Web Crypto, passphrase entered by HR at the start of the session) rather than the raw spreadsheet. Known limitations: paper has no confidentiality, the kiosk needs a staffed PC and printer, and two-factor lookup is only as good as the secrecy of birth dates and PINs.

**Priority 5: mail-merge export packs for the employers who can use them.** Ship a "Thunderbird Mail Merge pack": the flat folder of PDFs plus a `mailmerge.csv` with `Email`, `Name`, `Period`, `Attachment` columns and a one-page instruction that covers installing Thunderbird ESR, adding the mailbox, multi-selecting the PDFs in Browse, setting a pause of 3–7 seconds to stay under Exchange's 30 messages per minute, and using "Save as Draft" for a review pass. Ship a classic-Outlook pack alongside it: the `.eml` files zipped in batches of 50 (each with `X-Unsent: 1`, a unique `Message-ID`, an RFC 2047 subject and a UTF-8 body) and a ready-to-paste VBA module that saves to Drafts rather than sending, with a note that it needs classic Outlook, a self-signed macro certificate, and an administrator if Trust Center is policy-locked. Warn in both packs about provider quotas and the 100-external-recipient cap on `onmicrosoft.com` domains. Known limitations: these packs serve office staff with mailboxes, not site labour; new Outlook breaks both; Thunderbird's Experiment add-ons stop on the release channel from version 153, so ESR is the stated target.

Two cross-cutting items belong in every tier. The workbook template should gain a "Delivery" column (WhatsApp, email, paper/kiosk) and a "Channel consented on" date, so the manifest and log record the basis for each hand-off and the privacy notice can be issued in Arabic, as the draft PDPL regulations anticipate. And the compliance text shipped with the app should state plainly that Saudi law does not prescribe a payslip format, signature or medium; that the slip mirrors the Mudad wage file; and that the exported log, not a signature, is the employer's proof.

## Conclusion

The research reframes the problem. "Bulk delivery from a browser" is not a feature the platform withholds for lack of effort; it is excluded by design, through user-activation rules that exist precisely to stop a web page from sending or saving a thousand things at once. The productive response is to stop treating the app as a sender and treat it as the fastest possible preparer: files named so that every other tool can match them, a send list that reduces each hand-off to one gesture, and a log that turns those gestures into evidence. Measured that way, the app's real competitor is not a mail server but the clerk's time, and the honest comparison for an employer is a day of clicking per month against roughly fifteen dollars of paid WhatsApp API or a ream of paper.

The second shift is where the risk sits. The technical constraints point toward WhatsApp because that is where the workers are; the legal constraints point away from it, because every message is a foreign-hosted disclosure of salary data with a 72-hour breach clock and no adequacy decision behind it, while the paper register and the camp-office kiosk, the lowest-tech options on the list, are also the cleanest under PDPL and the most legible to an inspector. A delivery feature set that defaults to local export and collection, offers WhatsApp with guard-rails for the workers who choose it, and records the choice per worker is both the safest and, for a thousand-person camp, the fastest.
